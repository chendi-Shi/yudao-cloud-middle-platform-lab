# 并发全局事务压测：AT 的成本到底在哪

> 问题：Seata AT 的代价，主要来自「全局锁竞争」，还是来自「AT 本身的协议开销」？
> 结论先说：**主要是协议开销；锁竞争只在尾延迟上叠加，而且会让尾延迟极不稳定。**

## 一、实验设计

四个场景，两两对照，唯一变量是「有没有全局事务」和「是不是同一行」：

| # | 场景 | 说明 |
| --- | --- | --- |
| A | `no-tx` + 不同账户 | 基线：同样两步操作，不开全局事务，锁不冲突 |
| B | `no-tx` + 同一账户 | 只有数据库行锁，没有全局锁 |
| C | `at` + 不同账户 | 有 AT 协议开销，但锁不冲突 |
| D | `at` + 同一账户 | AT 协议开销 + 全局锁竞争（最坏情况） |

- 操作：`place-order`（订单写入 `yudao_seata_order` + Feign 调 infra 扣余额 `yudao_seata_account`），金额 1 分
- 对照组接口：`/place-order-no-tx`，代码完全相同，只去掉 `@GlobalTransactional`
- 规模：80 请求 / 20 并发，每个场景跑 2 次
- 工具：`script/seata/lock-bench.py`（aiohttp，记录逐请求耗时）
- 环境：单机、单 MySQL、Seata Server file 存储、客户端与服务端同机

## 三、结论

### 1. AT 的协议开销是主要成本：吞吐降到约 1/4

| 对比 | 吞吐 | p99 |
| --- | --- | --- |
| 不同账户：no-tx → AT | 250 → 65 rps（**−74%**） | 124 → 450 ms（**+3.6 倍**） |
| 同一账户：no-tx → AT | 200 → 52 rps（**−74%**） | 150 → 700 ms（**+4.7 倍**） |

这部分开销来自：每个分支要连 Seata Server 注册、写 `undo_log`（含前后镜像的 JSON 序列化）、提交后异步清理、二阶段协调。**它和锁无关，只要用了 AT 就要付。**

### 2. 全局锁竞争是「叠加项」：主要打在尾延迟上

| 对比（都在 AT 下） | 吞吐 | p99 |
| --- | --- | --- |
| 不同账户 → 同一账户 | 65 → 52 rps（−20%） | 445 → 725 ms（**+63%**） |
| 对照（不开 AT）：不同 → 同一账户 | 250 → 200 rps（−20%） | 124 → 152 ms（+23%） |

两个有意思的点：

- **吞吐的影响两者差不多（都是 −20%）**，因为无 AT 时同一行也要抢 InnoDB 行锁，本来就会串行化；
- **p99 的劣化 AT 明显更重（+63% vs +23%）**，因为全局锁的等待是在「本地事务已提交之后」发生的，等待时间全部叠加在响应时间上，而且持锁方还要完成二阶段。

### 3. 尾延迟极不稳定，这是最危险的地方

同一账户下，两轮压测的 p99 是 **921 ms 和 529 ms**——同一份代码、同样的负载，差了 74%。这就是「锁排队」的典型特征：一旦有几个慢请求持锁，后面全部堆积，延迟雪崩式放大。

**对生产的含义**：AT 场景里，热点行的 p99 是不可预测的，不能只看平均值做容量规划。要么拆行（分段账户），要么把热点操作从全局事务里移出去（异步化 + 本地消息表）。

## 四、这些数字不能怎么用

1. **Seata Server 是 file 单机存储**，没有集群和 db 存储，二阶段性能不代表生产
2. **客户端与服务端同机**，没有网络 RTT，所以真实环境的 AT 开销只会更大
3. **单机单库**，没有考虑跨机房、连接池打满等真实约束
4. **没有做 JVM 预热**，第一轮普遍比第二轮慢（可以看到 A 组 run1 明显差于 run2）
5. 金额 1 分、行很小，undo_log 序列化开销被低估

## 五、如果继续优化，我会做什么

1. **拆热点**：账户按 `user_id % N` 拆成 N 个子账户，把同一行的竞争打散
2. **缩小全局事务边界**：只把「必须原子」的两步放进 `@GlobalTransactional`，通知、积分等改为消息
3. **对账兜底**：AT 不是 100% 可靠（极端情况下需要人工介入），关键业务要加对账任务
4. **压到饱和点**：本次是固定请求数，应该用固定时长 + 逐步加压，找吞吐拐点

## 六、复现

```bash
cd yudao-cloud
# 准备：20 个账户，每个余额 100 万
docker exec yudao-cloud-mysql-1 mysql -uroot -pRoot@Yudao2026 -e "UPDATE yudao_seata_account.demo_seata_account SET balance = 1000000 WHERE tenant_id = 1;"

# 四个场景，各跑两次
for ep in tx no-tx; do for mode in same distinct; do
  python3 script/seata/lock-bench.py --endpoint $ep --mode $mode --n 80 --c 20
done; done
```

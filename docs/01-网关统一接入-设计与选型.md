# 网关统一接入层：设计与选型

> 改造范围：`yudao-gateway` + `yudao-spring-boot-starter-security` + `yudao-common`
> 对应提交：`c7ff743`（限流）、`f32329c`（内部签名）、`70e4caa`（灰度分流）

## 一、全景：一个请求进来要过几道关

改造前，网关基本是个「透明路由器」：解析 token → 转发。真正的权限判断、限流、防绕过全靠各业务服务自己。

改造后，网关变成三层闸门，每层只做一件事，且都能独立开关：

```
                        ┌──────────────────────── 网关（48080）────────────────────────┐
  浏览器 / App          │                                                              │
      │                 │  ① TokenAuthenticationFilter  order=-100                     │
      │  Authorization  │     解析 token → 调 system-server 校验 → 写 login-user 头     │
      ├────────────────►│                                                              │
      │  tenant-id      │  ② RateLimitFilter           order=-50   ← 新增              │
      │                 │     Redis+Lua 令牌桶，维度=租户+用户，超限 429                  │
      │                 │                                                              │
      │                 │  ③ GrayRoutingFilter         order=-20   ← 新增              │
      │                 │     用户哈希取模 → 写 header[version]，交给 LB 选实例          │
      │                 │                                                              │
      │                 │  ④ InternalSignFilter        order=-10   ← 新增              │
      │                 │     HMAC(ts,nonce,method,path) → 三个签名头                   │
      │                 │                                                              │
      │                 │  ⑤ 路由 / 负载均衡（grayLb://）                              │
      └────────────────►└──────────────────────────────┬───────────────────────────────┘
                                                       │
                    ┌──────────────────────────────────┼──────────────────────────────┐
                    ▼                                  ▼                              ▼
            system-server(48081)              infra-server(48082)            ... 其他服务
            ┌──────────────────────┐          ┌──────────────────────┐
            │ InternalSignVerifier │ ← 新增   │ InternalSignVerifier │
            │ 验签 → 401 拦截      │          │                      │
            ├──────────────────────┤          ├──────────────────────┤
            │ Spring Security 链   │          │ Spring Security 链   │
            │ @PreAuthorize 鉴权   │          │                      │
            └──────────────────────┘          └──────────────────────┘
                    │                                  │
                    └──────────► MySQL 13306 / Redis 16379 / Nacos 8848
```

**关键设计：三类入口分开对待**

| 路径 | 谁在调 | 要不要签名 | 要不要限流 |
| --- | --- | --- | --- |
| `/admin-api/**` | 管理后台 → 网关 | 要 | 要 |
| `/app-api/**` | C 端 App → 网关 | 要 | 要 |
| `/rpc-api/**` | 服务之间 Feign 直连 | 不要 | 不要 |
| `/actuator/**` | 运维探针 | 不要 | 不要 |

这个划分不是拍脑袋：`/rpc-api/**` 本来就不经过网关，如果也强制签名，Feign 调用链会全部 401；而 `/actuator/**` 签名会导致 K8s 探针失败、服务被误杀。

## 二、改造点 1：Redis + Lua 令牌桶限流

**文件**

```
yudao-gateway/
├── src/main/java/.../filter/ratelimit/
│   ├── RateLimitProperties.java     # 配置：开关/QPS/桶容量/规则/维度
│   ├── TokenBucketRateLimiter.java  # Redis + Lua 执行
│   └── RateLimitFilter.java         # GlobalFilter，order=-50
└── src/main/resources/lua/rate_limit_token_bucket.lua
```

**行为**

1. 请求进来 → 按 Ant 规则匹配 path（`/admin-api/system/auth/login` 单独限 5 QPS，其余用默认值）
2. 组装 key：`yudao:gateway:ratelimit:{规则}:t:{tenantId}:u:{userId}`，未登录退化为 `ip:{clientIp}`
3. Lua 原子执行：取桶 → 按流逝时间补令牌 → 够则扣 1 放行，不够则拒绝
4. 放行时回写 `X-RateLimit-Limit` / `X-RateLimit-Remaining`；拒绝时 `429 + Retry-After: 1`

## 三、改造点 2：内部调用 HMAC 签名

**为什么需要它**：网关鉴权后，服务端口在内网仍然可直连（开发环境、K8s 同命名空间、误配的 LB），攻击者可以完全跳过网关，直接伪造 `login-user` 头冒充任意用户。

**协议**

```
payload   = ts + "\n" + nonce + "\n" + METHOD + "\n" + path
signature = hex(HmacSHA256(secret, payload))

请求头：
  X-Yudao-Ts    毫秒时间戳
  X-Yudao-Nonce 随机 32 位
  X-Yudao-Sign  签名
```

**服务端校验顺序（顺序很重要）**

```
① 三个头是否齐全           → 缺 → 401
② |now - ts| <= 60s        → 超窗 → 401
③ HMAC 校验（常量时间比较） → 不符 → 401
④ nonce 是否首次使用(Redis SETNX 120s) → 重复 → 401
```

先验签再查 nonce，是因为反过来的话，攻击者可以用随机 nonce 把 Redis 打爆。

**文件**

```
yudao-framework/yudao-common/.../util/sign/InternalSignUtils.java   # 共享算法契约
yudao-gateway/.../filter/security/InternalSignFilter.java           # 网关侧签名
yudao-framework/yudao-spring-boot-starter-security/
├── .../core/sign/InternalSignProperties.java
├── .../core/sign/NonceStore.java          # Redis 实现 + 单机兜底
├── .../core/sign/InternalSignVerifier.java
└── .../config/InternalSignAutoConfiguration.java
```

## 四、改造点 3：按比例的灰度分流

上游 `GrayLoadBalancer` 只会「按 header[version] 匹配 metadata[version] 选实例」，但**没人决定谁该带这个 header**。我补的是决策层：

- 配置 `yudao.gateway.gray.rules: [{version: v2, percent: 20}]`
- 过滤器中：登录用户取 `userId`，未登录取 IP → Murmur3 哈希 → `% 100` → 落在 `[0,20)` 走 v2
- 结果写入 `header[version]` 与响应头 `X-Gray-Version`，后续选实例完全复用上游逻辑

## 五、选型决策表（面试重点）

> 这是整个改造里最值钱的部分：每个「用 A 不用 B」都要能说出**约束条件**和**代价**。

### 1. 限流算法：令牌桶 vs 固定窗口 / 滑动窗口 / 漏桶

| 方案 | 优点 | 致命问题 | 结论 |
| --- | --- | --- | --- |
| 固定窗口 | 实现最简单，一个 INCR+EXPIRE | 窗口切换临界点有 **2 倍突刺**（59 秒打满 + 61 秒打满 = 2 倍） | 否决 |
| 滑动窗口 | 无突刺 | 需存每请求时间戳或分桶，Redis 内存/计算开销大 | 否决（本场景不值） |
| 漏桶 | 输出绝对平滑 | 不允许突发，秒杀类正常业务流量也会被削平 | 否决 |
| **令牌桶** | 既限平均速率，又用「桶容量」显式表达可接受突发 | 需自己实现 | **采用** |

**为什么选令牌桶**：登录接口允许「平时 5 QPS，但用户手抖连点 10 次不该被拦」，这个语义正好是「容量 10 的桶」。

### 2. 计数器放哪：Redis vs 网关本地内存

选 **Redis**。理由：网关是多实例部署，本地 `Guava RateLimiter` 是「每实例 100 QPS」，3 个实例就是 300，集群级阈值根本限不住；且实例重启/扩缩容会重置桶。

**代价**：每个请求多一次 Redis 往返（约 0.1~0.3ms），且强依赖 Redis 可用性 → 所以配了 `fail-open`。

### 3. 原子性：Lua vs Java `GET`+`SET` vs 分布式锁

选 **Lua**。`GET` 和 `SET` 之间有窗口，并发下多个请求读到同一个令牌数，会**超卖**（limit 100 实际放过 130）。加分布式锁能解决但要多一次往返 + 锁竞争。

**Lua 的本质收益**：Redis 单线程执行整段脚本，天然串行，等于「免费」拿到了原子性。

### 4. 时间戳：应用传入 vs Lua 里 `redis.call('TIME')`

选 **应用传入**。`TIME` 在 Redis 5+ 脚本里属于非确定性命令，复制/AOF 重放时行为不一致（Redis 会拒绝或告警）；多实例时钟漂移在「秒级限流」里完全可忽略。

### 5. 限流位置：网关 vs 服务内 vs Sentinel

选 **网关**。中台有几十个服务，限流规则写在每个服务里 = 规则分散、口径不一、改一次要发几十个包。网关一处配置即可覆盖全部入口。

**没选 Sentinel 的原因**（诚实版）：Sentinel 更擅长「熔断/降级/热点参数限流」，但它需要额外部署控制台、规则要推送到每个服务；本项目只需要「入口级 QPS 保护」，用 Redis+Lua 20 行就能覆盖，且规则可以随配置中心热更新。**如果要做熔断、异常比例降级、热点 key 限流，我会换 Sentinel。**

### 6. 故障策略：fail-open vs fail-close

默认 **fail-open**（Redis 挂了就放行）。理由是：中台网关挂掉是 P0，限流失效只是「少了一层保护」；反过来 fail-close 会让 Redis 抖动放大成全站不可用。配置项 `fail-open: false` 留给安全优先场景（如支付入口）。

### 7. 拒绝用 429 而不是 503

429 = "你太快了，慢点再来"（带 `Retry-After`，客户端可退避重试）；503 = "服务不可用"（客户端通常直接放弃/告警）。限流是**预期行为**，不是故障。

### 8. 防绕过：HMAC 签名 vs mTLS vs JWT vs 纯网络隔离

| 方案 | 强度 | 成本 | 结论 |
| --- | --- | --- | --- |
| 纯网络隔离（只开内网） | 中 | 低 | 单靠它不够：内网横向移动、误配暴露都常见 |
| mTLS | 高 | 高（证书签发/轮换/服务网格） | 中台规模值得，但校招项目做不出来 |
| JWT 内部令牌 | 中 | 中（体积大、需签发中心） | 内部调用不需要承载用户身份，浪费 |
| **HMAC 签名** | 中高 | 低（共享密钥） | **采用**，够用且能讲清原理 |

### 9. 签名内容：只签时间戳 vs 签 method+path

必须签 **method + path**。只签时间戳的话，攻击者可以拿一个「查询订单」的合法签名去调「删除订单」接口（签名与接口无关）；把 method+path 纳入摘要后，签名与具体接口绑定。

**顺带一个细节**：payload 用 `\n` 分隔而不是直接拼接，是为了避免歧义拼接 —— `ts=1,nonce=23` 和 `ts=12,nonce=3` 拼起来都是 `"123"`，单测里专门覆盖了这个 case。

### 10. nonce 存储：Redis vs 进程内存

生产必须 **Redis**（多实例共享，SETNX 天然去重）。但框架层不能强依赖 Redis，所以用 `ObjectProvider` 判断：有 Redis 用 Redis，没有则降级 Guava 缓存并打 WARN —— 代价是多实例下防重放失效，属已知降级。

### 11. 校验范围：全部路径 vs 只 `admin-api`/`app-api`

只校验外部入口。全量校验会打死 Feign 的 `/rpc-api/**` 调用（它们不经过网关），也会误伤 `/actuator/**` 健康检查导致服务被摘除。

### 12. 签名算法放哪：`yudao-common` 共享 vs 网关/服务各写一份

选 **共享**。网关是 WebFlux（不能引 servlet 依赖），服务端是 servlet，如果把算法写进 `starter-security`，网关就无法复用 → 两边各写一份必然出现「一边改了另一边没改」的签名漂移。放到无依赖的 `yudao-common` 里，两边引同一个类，契约只有一份。

### 13. 灰度 key：userId vs IP vs 随机

选 **userId**。随机数会让同一用户每次刷新在 v1/v2 之间跳（体验割裂、问题无法复现）；IP 在移动端会随基站切换而变。userId 才是稳定标识，未登录才退化 IP。

### 14. 灰度决策放哪：网关 Filter 写 header vs 改 LoadBalancer

选 **Filter**。LoadBalancer 的职责是「给定条件选实例」，让它同时负责「决定条件」会让它变成上帝类；而且 Filter 里能拿到 `LoginUser`（LB 只有 headers），取 userId 更自然。**职责分离的收益**：分流比例改配置即可，选实例逻辑一行不用动。

### 15. 响应式：`ReactiveStringRedisTemplate` vs 阻塞模板 + `boundedElastic`

网关是 WebFlux，事件循环线程数量很少（默认 = CPU 核数）。用阻塞 Redis 模板就必须切到 `boundedElastic` 线程池，高并发下线程池排队会把延迟放大（实测同类场景 P99 能差 2~3 倍）。多引一个 `spring-boot-starter-data-redis-reactive` 换来全链路非阻塞，值得。

## 六、配置速查

```yaml
yudao:
  gateway:
    rate-limit:
      enabled: true            # 开关
      fail-open: true          # Redis 故障时放行
      default-qps: 100         # 每秒补充令牌
      default-capacity: 200    # 桶容量 = 允许突发
      dimension: TENANT_USER   # TENANT_USER / IP
      rules:
        - path: /admin-api/system/auth/login
          qps: 5
          capacity: 10
    internal-sign:
      enabled: true
      secret: ${INTERNAL_SIGN_SECRET}
      paths: [/admin-api/**, /app-api/**]
    gray:
      enabled: false
      header-name: version
      rules: [{version: v2, percent: 20}]
```

环境变量对应（`local-dev.sh` 已配好）：
`YUDAO_GATEWAY_RATE_LIMIT_ENABLED` / `YUDAO_GATEWAY_INTERNAL_SIGN_ENABLED` / `YUDAO_SECURITY_INTERNAL_SIGN_ENABLED` / `INTERNAL_SIGN_SECRET` / `YUDAO_GATEWAY_GRAY_ENABLED`

## 七、验证方式（可复现）

```bash
# ① 签名：直连服务应 401
curl -X POST http://127.0.0.1:48081/admin-api/system/auth/login \
  -H 'Content-Type: application/json' -H 'tenant-id: 1' \
  -d '{"username":"admin","password":"admin123"}'
# → {"code":401,"msg":"内部调用签名校验失败：缺少内部调用签名头..."}

# ② 经过网关应成功
curl -X POST http://127.0.0.1:48080/admin-api/system/auth/login ...   # → 200 + token

# ③ 限流：30 并发打登录（qps=5, cap=10）→ 10 个 200，20 个 429
seq 1 30 | xargs -P 30 -I{} curl -s -o /dev/null -w '%{http_code}\n' ... | sort | uniq -c

# ④ 防重放：用同一 nonce 手工构造两次合法签名 → 第二次 401
# ⑤ 灰度：100% 配置下响应头出现 X-Gray-Version: v2
```

## 八、局限（面试被追问时主动说）

1. **单实例压测**：所有数字来自单 system-server + 单网关，没有验证多实例下限流桶的集群一致性（逻辑上成立，但没实测）
2. **签名密钥是静态共享密钥**：生产应该走 KMS/Vault 轮换，且支持双密钥灰度轮换（新老密钥并存）
3. **灰度只做了单版本**：没有做「多版本并存 + 按租户白名单」的完整能力
4. **没有接 SkyWalking**：链路追踪没做，实际排障时定位慢请求会麻烦
5. **限流是入口级**：没有做「按接口成本加权」（比如导出接口消耗 10 个令牌，查询消耗 1 个）

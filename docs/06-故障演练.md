# 故障演练：三个真实的故障场景

> 目的：验证「设计时的降级逻辑」在真实故障下到底成不成立。
> 结论先说：**实例宕机扛住了，Nacos 短时故障扛住了，Redis 故障没扛住——fail-open 只解决了限流层，救不了鉴权链路。**

## 一、演练方法

| 项 | 值 |
| --- | --- |
| 环境 | 网关 ×1、system-server ×2（48081/48083）、infra-server ×1 |
| 客户端 | `curl`（单请求）+ Python aiohttp（1200 请求、20 并发） |
| 判定 | 以 **HTTP 状态码统计** 为准，不看压测工具的 `Failed requests` |
| 恢复 | 每轮演练后恢复组件，并验证 200 |

## 二、演练 1：服务实例宕机

**操作**：两实例正常运行，`kill -9` 掉 48083 的监听进程，同时打 1200 个请求（20 并发）。

**结果**：

```
1200 个请求：状态码 {200: 1200}，异常 0，耗时 6.97s
Nacos 实例数：2 → 1，耗时 < 1 秒
恢复采样：宕机后 0~15 秒，每秒 10 个请求，全部 200
```

**结论**：Nacos 的 gRPC 长连接一断开，实例变更几乎立刻推送到网关，**网关侧的失败窗口小于 1 秒**，1200 个请求零失败。

**这里有个重要的方法论陷阱**：同一动作下 `ab` 报「Failed requests: 598」，而能记录状态码的客户端是 0 失败。`ab` 把连接中断、长度不一致都计入失败，在这个场景里不可信。**做故障演练必须能逐请求看到状态码，否则会得出相反结论。**

**还有一次误操作值得记录**：第一次我用 `lsof -ti:48083` 取进程号，结果把**网关**也杀了——`lsof` 默认会列出所有占用该端口的进程，包括作为客户端连接上来的网关。正确写法是：

```bash
lsof -ti :48083 -sTCP:LISTEN    # 只要监听方
```

## 三、演练 2：Redis 故障（最关键的一组）

**操作**：`docker stop` 掉 Redis，观察限流与鉴权。

**结果**：

```
网关日志：5 条 [filter][限流器异常，fail-open 放行]   ← 降级逻辑生效
短超时（8s）请求：5/5 返回 000（客户端超时）
长超时（30s）单请求：HTTP 500，耗时 10.72s，body = {"code":401,"msg":"账号未登录"}
恢复 Redis 后：3/3 返回 200
```

**结论**：

1. **fail-open 按设计生效**：限流器拿不到 Redis 时不会拦请求，网关不会因为限流组件故障而全站 429/503。
2. **但全站仍然不可用**：`TokenAuthenticationFilter` 校验 token 需要读 Redis，Redis 挂掉后请求在鉴权环节卡住约 10.7 秒，最终失败。
3. **所以「fail-open」只是限流层的降级，不是系统的高可用**。真正的结论是：**Redis 是鉴权链路的单点**。

如果要让这套架构扛住 Redis 故障，需要：

- Redis 做哨兵/集群（消除单点）
- token 校验加本地缓存（牺牲一点一致性换可用性，注意吊销延迟）
- 给 Redis 客户端设置**短超时**（现在是 10.7s，用户早就走了）

## 四、演练 3：注册中心（Nacos）宕机

**操作**：`docker stop` Nacos，持续 30 秒，期间每秒采样。

**结果**：

```
Nacos 停止后 0s / 2s / 5s / 10s / 20s / 30s：全部 5/5 成功
Nacos 恢复后：5/5 成功，服务列表重新变为 3 个（system-server / gateway-server / infra-server）
```

**结论**：网关和业务服务都依赖 Nacos 客户端的**本地服务列表缓存**，短时（30 秒级）故障不影响已有路由；但故障期间**实例上下线不可见**——如果此时有服务重启，它的新地址不会被感知，可能出现流量打到已下线实例。

这也解释了为什么网关的 `TokenAuthenticationFilter` 里有一层 Guava 缓存：**缓存是这类架构的默认兜底手段**，不是优化。

## 五、附带发现：网关本身是单点

第一次误杀网关时，所有请求 100% 失败（`ok=0 fail=20`）。这是预期内的——但值得写下来：**当前架构里网关没有多副本、没有 VIP/负载均衡器**，网关进程挂掉就是全站不可用。生产上至少要做双实例 + 前面挂 SLB。

## 六、结论汇总

| 故障 | 设计预期 | 实测 | 是否达标 |
| --- | --- | --- | --- |
| 单个服务实例宕机 | 无感切换 | 1200 请求 0 失败，摘除 <1s | ✅ |
| Redis 故障 | fail-open 放行 | 限流放行 ✅，但鉴权 10.7s 后失败，全站不可用 | ⚠️ 部分达标 |
| Nacos 短时宕机 | 本地缓存兜底 | 30s 内 5/5 成功，恢复后自动重注册 | ✅ |
| 网关自身宕机 | 未设计 | 100% 失败 | ❌ 单点 |

## 七、如果继续做

1. **Redis 高可用**：哨兵模式 + 客户端短超时（`spring.data.redis.timeout=500ms`）+ token 本地缓存
2. **网关多副本**：起 2 个网关实例 + 一个 Nginx 做 VIP，再演练一次「杀网关」
3. **给 LB 配重试**：`spring.cloud.loadbalancer.retry.enabled=true`，把「摘除窗口内」的失败也兜住
4. **演练自动化**：把这三组演练写成脚本，纳入 CI 的 nightly job（`workflow_dispatch` 手动触发）

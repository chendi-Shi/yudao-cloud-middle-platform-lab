# 网关限流压测报告

> 目的：回答三个问题 —— 限流**有没有用**、**代价多大**、**数据怎么读才不骗自己**。

## 一、环境与方法

| 项 | 值 |
| --- | --- |
| 机器 | Apple M4 Pro / macOS |
| JDK | Temurin 17.0.21 |
| 框架 | Spring Boot 3.5.15 + Spring Cloud Gateway（WebFlux） |
| 中间件 | MySQL 8.4 / Redis 7.4 / Nacos 3.0.3（Docker Desktop） |
| 部署 | 网关 ×1、system-server ×1、infra-server ×1（**单实例**） |
| 压测工具 | `ab`（Apache Bench 2.3），`-n 3000 -c 50` |
| 被测接口 | `GET /admin-api/system/user/page?pageNo=1&pageSize=2`（走网关 → Nacos → system-server → MySQL） |
| 连接复用 | 未开启 keep-alive（`ab` 默认每个请求新建 TCP），因此延迟含握手开销 |

三组场景，每组之间重启网关切换配置（同机同库，排除环境差异）：

| 场景 | 限流 | QPS 阈值 | 桶容量 |
| --- | --- | --- | --- |
| A 基线 | 关闭 | — | — |
| B 保护 | 开启 | 100 | 200 |
| C 开销 | 开启 | 100000 | 200000 |

## 二、结果

### A 基线（限流关闭，跑两次看波动）

| 轮次 | 吞吐 | P50 | P90 | P99 | 失败 |
| --- | --- | --- | --- | --- | --- |
| A1 | 621.41 req/s | 73 ms | 129 ms | 189 ms | 0 |
| A2 | 662.22 req/s | 70 ms | 114 ms | 175 ms | 0 |

两次差异约 6%，作为后续判断「是否有性能影响」的噪声基线。

### B 限流开启：100 QPS / 桶 200

| 指标 | 值 |
| --- | --- |
| 总请求 | 3000 |
| 放行（200） | **355**（11.8%） |
| 拒绝（429） | **2645**（88.2%） |
| 其他失败 | 0 |
| 整体吞吐 | 2461 req/s（含被拒请求） |
| P99 | 129 ms |

355 ≈ 桶容量 200 + 1.5 秒 × 100 QPS，与设计预期一致。

### C 限流开启但阈值打满（隔离「限流本身」的开销）

| 轮次 | 吞吐 | P50 | P90 | P99 | 失败 |
| --- | --- | --- | --- | --- | --- |
| C1 | 658.72 req/s | 72 ms | 108 ms | 145 ms | 0 |
| C2 | 697.94 req/s | 68 ms | 96 ms | 130 ms | 0 |

## 三、结论

### 1. 限流确实把后端保护住了

88.2% 的流量在网关就被拒掉，只有 355 个请求打到 system-server。如果没有限流，3000 个请求会全部落到数据库连接池（Druid max-active=20）上——这正是中台被刷垮的典型路径。

### 2. 限流本身的开销可以忽略

C 组 658~698 req/s vs 基线 621~662 req/s，差异 **+5% 左右，落在 6% 的轮次波动内**。

原因很直白：一次 Redis Lua 往返约 0.2 ms，而单请求本身要 1.5 ms（含网关转发 + Feign 校验 token + MySQL 查询），占比不到 15%，被淹没在噪声里。

**这组数据的方法论价值**：想证明「加了组件没拖慢」，必须测「开着但阈值打满」，而不是「关上 vs 打开就限死」——后者测的是保护效果，不是性能。

### 3. 一个必须警惕的数据陷阱：429 会让 QPS 虚高

B 组的 2461 req/s 是**假吞吐**：被拒请求不进后端，1 ms 内就返回，把平均吞吐拉高了近 4 倍。

> 如果只看 `Requests per second`，会得出「限流让吞吐提升 3.7 倍」的荒谬结论。

**正确读法**：同时看 `Non-2xx responses`，用「放行数 / 总时长」算真实通过量（本场景 ≈ 355 / 1.22s ≈ 290 req/s，含初始突发）。

我第一次跑就踩了这个坑：脚本的变量名传错，基线其实开着限流，得到「1476 req/s + 1658 个非 2xx」的诡异组合，差点写成「基线性能更好」。

### 4. 单实例的局限（不要过度解读）

- 单机单实例，没有网络延迟、没有跨可用区，绝对数值不可外推
- 没开 keep-alive，P99 含 TCP 握手开销，真实 P99 会更低
- 没压到系统饱和点：RPS 曲线在 662 就停是因为 `ab` 用固定请求数而非固定时长

## 四、如果要继续做

1. 用 `wrk -t4 -c200 -d60s` 固定时长压，画出「并发 - QPS - P99」曲线，找到拐点
2. 起 2~3 个 system-server 实例，验证「单实例限流 100 QPS」vs「集群共享桶 100 QPS」的差异（这是选 Redis 而非本地限流器的直接证据）
3. 加一组对照：`fail-open` 时手动停掉 Redis，看网关是否仍能转发（验证降级逻辑）

## 五、复现命令

```bash
# 基线
cd yudao-cloud
pkill -f yudao-gateway.jar
YUDAO_GATEWAY_RATE_LIMIT_ENABLED=false nohup ./local-dev.sh gateway > logs/gw.log 2>&1 &
# 等健康检查通过后
ab -n 3000 -c 50 -H "Authorization: Bearer <token>" -H "tenant-id: 1" \
   'http://127.0.0.1:48080/admin-api/system/user/page?pageNo=1&pageSize=2'

# 限流开启（100 QPS / 200 桶）
YUDAO_GATEWAY_RATE_LIMIT_ENABLED=true \
YUDAO_GATEWAY_RATE_LIMIT_DEFAULT_QPS=100 \
YUDAO_GATEWAY_RATE_LIMIT_DEFAULT_CAPACITY=200 \
nohup ./local-dev.sh gateway > logs/gw.log 2>&1 &
```

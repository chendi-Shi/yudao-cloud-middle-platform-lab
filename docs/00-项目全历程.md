# 项目全历程：从选题到上线，包括所有踩过的坑

> 这份文档记录**过程**，不是结论。结论在 README，选型推导在 01/03，数据在 02/05/06。
> 写它的原因：面试官问的往往不是「你做了什么」，而是「你卡在哪、怎么出来的」。

---

## 一、时间线（12 个阶段）

### 阶段 0：选题 —— 4 选 1，再砍掉一半

候选：`yudao-cloud`（19.8k★）、`mall-swarm`（13.2k★）、`lamp-cloud`（5.7k★）、`RuoYi-Cloud`（1.8k★）。

选 yudao 的理由：它有一套**自研的框架层**（`yudao-framework` 18 个 starter：多租户、数据权限、幂等、限流、MQ 封装），正好对应中台岗问的「通用能力沉淀」；另外三个要么是纯业务（mall），要么框架层薄（RuoYi）。

**分支选择**：默认 `master` 是 JDK 8 + Spring Boot 2.7，`master-jdk17` 是 JDK 17 + SB 3.5.15。选了后者——2027 届面试官看到 SB 2.7 会扣分。

**第一个「砍需求」**：原计划做「多租户线程上下文透传」，读代码发现 `TenantContextHolder` **已经用 `TransmittableThreadLocal`**，上游早解决了。于是放弃这个改造点，把精力转到真正缺失的网关治理层。

### 阶段 1：拿代码 —— git 协议在这台机器上不通

```bash
git clone https://github.com/YunaiV/yudao-cloud.git
# fatal: unable to access ...: Empty reply from server
```

`api.github.com` 和 `codeload.github.com` 都能通，只有 `github.com` 的 git 端口不行。改用源码包：

```bash
curl -L -o yudao-cloud.tar.gz https://codeload.github.com/YunaiV/yudao-cloud/tar.gz/refs/heads/master-jdk17
```

18MB → 解压 91MB → 7907 个 Java 文件、约 74 万行。**没有 .git 目录**，所以后面自己 `git init` 打了基线 commit。

### 阶段 2：环境 —— 机器上什么都没有

| 缺什么 | 怎么解决 |
| --- | --- |
| JDK | 无。brew 写 `/opt/homebrew` 被沙箱拦 → 下载 Temurin 17.0.21 到工作区 `.tools/` |
| Maven | 无。下载 3.9.9 到 `.tools/`，配阿里云镜像 |
| Maven 本地仓库 | `~/.m2` 不可写 → `-Dmaven.repo.local=工作区/.m2repo` |
| Docker | 装了但没启动 → `open -a Docker` |

**最坑的一步**：Adoptium 官方下载走 GitHub Release，10 分钟只下了 29MB；换清华镜像后 30 秒下完 178MB。

### 阶段 3：第一次跑通 —— 5 个坑连环

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| logback 报 `Failed to create parent directories for [/Users/bysx/logs/nacos/config.log]`，进程直接退出 | 日志写 `~/logs`，沙箱不可写 | `-Duser.home=工作区/home` + `LOGGING_FILE_NAME` + `-Dnacos.logging.path` |
| 登录报「验证码不能为空」 | 默认开启验证码 | `YUDAO_CAPTCHA_ENABLE=false` |
| Nacos 里建不了 `dev` 命名空间 | v1 console API 已废弃（410），v3 要鉴权 | 环境变量覆盖成 `public` |
| 连不上数据库 | `application-dev.yaml` 里 Redis 指向作者的 `400-infra.server.iocoder.cn` | 全部用环境变量覆盖 |
| 启动刷 9090 连接失败 | 本地没有 XXL-Job | `XXL_JOB_ENABLED=false` |

这几个坑最后都固化进了 `local-dev.sh`，别人 clone 下来不用再踩。

### 阶段 4：改造 A —— 网关限流

选型过程见 [docs/01](01-网关统一接入-设计与选型.md)。核心三个决定：

- **Redis 而不是本地令牌桶**：网关多实例，本地桶是「每实例 100 QPS」，3 个实例就是 300，集群阈值根本限不住
- **Lua 而不是 `GET`+`SET`**：check-then-act 有竞态，并发下会超卖令牌
- **fail-open 而不是 fail-close**：网关挂是 P0，限流失效只是少一层保护

### 阶段 5：改造 B —— 内部签名

先想清楚「防谁」：防的是**绕过网关直连服务端口**（开发环境、K8s 同命名空间、误配的 LB 都可能）。

- 用 HMAC 而不是 mTLS：证书体系做不出来，硬讲会露馅
- 签名必须含 `method + path`：否则签名可以被挪用到别的接口
- 只校验 `/admin-api`、`/app-api`：`/rpc-api` 是 Feign 直连，签了也没人验

### 阶段 6：改造 C —— 灰度分流

上游 `GrayLoadBalancer` 只会「按 header[version] 选实例」，但**没人决定谁该带这个 header**。我补的是决策层：userId 做 Murmur3 哈希取模。

- 用哈希不用随机：随机会让同一用户每次刷新都换版本
- 放 Filter 不放 LB：LB 只该负责「选实例」，不该同时决定「选哪个版本」

### 阶段 7：压测 —— 第一次数据是错的

第一版基线：`1476 req/s，1658 个非 2xx`。看起来「性能很好」，实际是脚本变量名传错，**基线其实开着限流**——1658 个请求是 429，廉价响应把 QPS 抬高了 4 倍。

修正后基线 621~662 rps、P99 175~189ms。这次教训写进了 [docs/02](02-压测报告.md)：**限流压测必须同时看 2xx 比例，不能只看吞吐。**

### 阶段 8：Seata —— 官方材料 + 4 个坑

仓库自带 `script/seata/` 接入材料（订单在 system-server、扣余额在 infra-server），省了造场景的时间。但接入过程踩了 4 个坑：

1. **Controller 放错包 → 404**：yudao 只给 `controller.admin.**` 加 `/admin-api` 前缀，日志是 `No static resource`
2. **双重数据源代理**：Seata 自动代理 + dynamic-datasource 代理会打架，必须关 `enable-auto-data-source-proxy`
3. **版本冲突**：不能用 Spring Cloud Alibaba BOM 管理的 Seata 版本，要显式 `org.apache.seata:2.6.0` 并排除 druid
4. **忽略 `CommonResult` 会让回滚失效**：Feign 返回错误码但 HTTP 200，不调 `getCheckedData()` 就当成成功提交了

### 阶段 9：前端 —— 只是为了截图，但暴露了真问题

pnpm 版本要求 `>=10.28.0`（先用 9 报错）、80 端口要 root（改 8090）、Chromium 在沙箱里要 `--no-sandbox` + `--user-data-dir`（默认写到 `~/Library` 被拦）。

**它其实是最高效的端到端测试**：签名 path 规范写错、限流阈值配错，页面立刻登录不进去。

### 阶段 10：灰度双实例 —— 差点用错证据

想证明「真的路由到了不同实例」，第一版用 Actuator 的 `http.server.requests` 指标，结果**指标列表是空的**（这个项目没采集 Web 指标）。改用 Tomcat access log 才拿到可逐行核对的证据。

另一个坑：**不能用「杀掉 A 实例」来验证**。`GrayLoadBalancer` 在「没有实例匹配 version」时会**回退到全部实例**，杀掉 A 后带 v2 的请求照样成功，看起来一切正常，其实什么都没证明。

### 阶段 11：发布 —— 三次被 GitHub 拦下

这是全程最折腾的一段，之前完全没记录：

1. **密钥扫描（第一次）**：上游 SQL 种子数据里有阿里云 AK，push 被 403
2. **密钥扫描（第二次）**：脱敏后还有腾讯云 SecretId、火山引擎 AK。分布在 9 个方言的 dump 里
3. **最终解决**：用 `git filter-branch` 做规则化脱敏（JSON 的 `accessKey/accessSecret` 字段 + 各厂商 key 前缀），**重写全部历史**——commit hash 全变了

然后又是凭证问题：`gh` 登录的是 `chendi-Shi`，但系统级 osxkeychain 里是另一个账号，一直 403；沙箱不让改全局 `.gitconfig`，最后用**仓库级 `credential.helper`** 在推送时向 `gh auth token` 取 token。

最后清理：`.flattened-pom.xml` 构建产物混进了基线提交（`git rm --cached`）、`actions/*@v4` 有 Node20 废弃告警（升 v5）。

### 阶段 12：质量闭环 —— 29 个测试 + CI + 三组演练

补了 20 个集成测试（含 Testcontainers 真实 Redis）、GitHub Actions CI、三组故障演练。演练又踩了三个方法论坑：

- `lsof -ti:48083` 把**网关**也杀了（它列出所有占用端口的进程，包括客户端）→ 正确是 `-sTCP:LISTEN`
- `ab` 在故障场景的 `Failed requests` 不可信（报 598，逐请求统计是 0）
- 测宕机影响前没关限流，676 个 429 被误当成宕机失败

## 三、决策总表（选了什么 / 否决了什么）

| 决策点 | 选择 | 否决 | 依据 |
| --- | --- | --- | --- |
| 项目底座 | yudao-cloud | mall-swarm / lamp-cloud / RuoYi-Cloud | 框架层最厚，对应中台岗考点 |
| 分支 | `master-jdk17` | `master`（JDK 8 + SB 2.7） | 2027 届简历不该出现 SB 2.7 |
| 限流算法 | 令牌桶 | 固定窗口 / 滑动窗口 / 漏桶 | 固定窗口有 2 倍临界突刺 |
| 计数存储 | Redis | 网关本地内存 | 多实例限不住集群总量 |
| 原子性 | Lua | `GET`+`SET` / 分布式锁 | check-then-act 会超卖 |
| 限流位置 | 网关 | 服务内 / Sentinel | 规则集中；Sentinel 强在熔断不是入口限流 |
| 故障策略 | fail-open | fail-close | 网关挂是 P0 |
| 拒绝码 | 429 | 503 | 语义是「退避重试」不是「服务故障」 |
| 防绕过 | HMAC | mTLS / JWT / 纯网络隔离 | 成本与强度的平衡 |
| 签名内容 | ts+nonce+method+path | 只签时间戳 | 防签名挪用到其它接口 |
| 校验范围 | admin/app | 全部路径 | 全量会打死 `/rpc-api` 和健康检查 |
| 灰度 key | userId 哈希 | 随机 / IP | 随机不稳定，IP 会变 |
| 灰度决策 | Filter 写 header | 改 LoadBalancer | 职责分离 |
| 分布式事务 | AT | TCC / 本地消息表 / 最大努力通知 | 零业务改造，短事务场景性价比最高 |
| 测试策略 | 单测 + 容器测试 + 状态码统计 | 只看压测工具报告 | ab 的失败计数不可信 |
| 发布 | 重写历史脱敏 | GitHub 白名单放行 | 密钥不该留在任何历史里 |

## 四、计划 vs 实际（偏差及原因）

| 原计划 | 实际 | 原因 |
| --- | --- | --- |

## 五、如果重做，会改什么

1. **先搭 CI 再写代码**：这次是最后补的，意味着中间所有改动都没有自动验证
2. **压测脚本先于功能写**：基线数据应该在动手前就采好，否则没法证明「改前 vs 改后」
3. **发布前本地先跑 secret scan**：不要等 GitHub 拦下来才处理，`git-secrets` / `gitleaks` 可以本地跑
4. **故障演练放进脚本**：现在是手工 `docker stop` + 循环 curl，应该写成可重复执行的脚本
5. **别用 `ab` 做故障场景**：它的计数规则不透明，换成能输出状态码的客户端

## 六、一句话总结

这个项目真正有价值的部分，不是「用了 Spring Cloud + Seata」，而是：**每一次卡住都有记录、每一个选择都有否决项、每一个结论都有能重跑的证据。**
